# Timed sales stock holds

## Scope and user decisions

A sales draft may now reserve the full quantity of every line at its fulfillment location. This is an explicit stock hold, separate from saving a draft or approving a sale. It does not move physical stock, approve credit, create a receivable, send a customer message or record payment. Duration defaults to 30 minutes; the staff UI also offers 2 hours and 24 hours. The API accepts whole-minute durations from 15 to 1440. There are no indefinite holds. A reason and a review are required for both hold and release.

Available pieces equal on-hand physical pieces minus all active, unclosed holds at that location/SKU. Expired holds stop reducing availability through a database time predicate; a worker, Redis or paid external service is unnecessary. Read results share the transaction's server timestamp and are displayed as a snapshot in Dhaka time. Refresh retrieves current values; writes always revalidate. Expiry status is derived from its recorded deadline even before a later request closes that expired history row. Replacement closes the old expired record and creates a separate new hold; an active hold cannot be silently extended or overwritten.

Inventory tables and SKU lookup now show on-hand, reserved and available separately. Existing all/positive/zero stock filters and summary totals continue to describe physical stock. The status badge distinguishes fully reserved stock. Generic reversal previews include reservations and prevent confirmation when the projected physical balance would fall below them. Actual posting rechecks under locks.

## Access and history

Global `sales.read` is required for the commercial order. Viewing its availability/history additionally requires `inventory.read` at its current fulfillment location. Without that stock grant the API returns an explicit hidden panel with no stock rows, hold reasons or historical quantities. Historical rows are filtered again by their original location scope. `sales.reserve` plus inventory read at the action's location controls hold/release; it need not grant editing prices or customer data. Fresh active/onboarded actor permissions are checked at the SQL boundary before cached retry. Authorized release remains possible after a location becomes inactive; otherwise stock could become stuck until expiry.

Hold records retain location, quantity/SKU/product snapshots, actor, reason, creation/deadline and release/expiry closure actor/reason/time. Read history is paginated independently of the current hold and availability. API/cache results contain only IDs, action and revision/version, not another contact/reason snapshot. Generic audit metadata contains entity/order IDs and reservation revision. A hold or release advances the order version and a separate reservation revision, preserving stale-form detection. Failed audit writes roll back every state change and retry key.

An active hold blocks editing or cancelling its draft. Staff must explicitly release the hold with the correct location permission before changing commercial lines/location or cancelling. Expired holds do not block draft edits. No customer debt or financial approval is implied by a stock hold; credit checks remain a confirmation/invoice acceptance gate.

## Concurrency and every deduction path

Migration 12 adds owner-controlled reservation state, history, lines, retry cache and an availability view. Runtime receives SELECT plus EXECUTE on one narrow SECURITY DEFINER posting function. It cannot directly modify hold tables, balances or commercial orders. The function uses a fixed `pg_catalog` search path and schema-qualified objects; actors/request IDs are supplied by server code.

Requests lock a separate idempotency namespace, then the order and its location/SKU balances in deterministic order. The full order must fit; a shortage rolls back the whole hold. No missing zero-balance rows are manufactured. Hold creation touches the existing balance row version without changing its physical quantity, and advances the order version before inserting the hold. These writes are deliberate: an older repeatable-read transaction must receive a serialization failure instead of using a snapshot from before the hold. Release reduces reservations and advances the order version without creating physical movements.

A database trigger prevents any balance decrease/delete/key move from consuming active reservations. It covers ordinary adjustments, transfers, generic reversals and purchase-receipt reversals through the existing shared stock core. Existing migrations/functions are not rewritten. A separate order-update guard prevents modifying a reserved draft through the old save function. A damaged/missing physical item requires releasing the affected commercial hold before recording its stock correction; the system does not silently overbook it. The restricted runtime role cannot disable these guards. Database-owner maintenance remains trusted operational work.

Reservation history prevents a destructive downgrade. The migration reverts only in an empty isolated schema. Production recovery requires a reviewed forward migration or a complete tested backup restore, not deleting stock/hold history.

## Verification and next boundary

Real PostgreSQL/HTTP tests cover global/scoped reads and actions, CSRF, concurrent identical retries, full multi-SKU atomicity, last-stock races between orders and against stock deductions, adjustment/transfer/reversal denial, older repeatable-read attempts, expiry/replacement, audit-failure rollback on hold and release, stale/revoked permissions, inactive-location release, runtime DML denial, strict durations, history pagination and compiled migration apply/revert/reapply. Existing stock and purchasing tests continue to verify the physical movement ledger. `npm run reservations:verify-local` checks active hold/order line consistency, availability bounds, history versions, revision/event counts and minimal retry shape without printing customer data or reasons.

Order confirmation, credit exposure, dispatch, invoices, customer payments and returns remain separate work. Dispatch will need to consume/release its own hold and post its source-linked physical movement in the same locked transaction, leaving other orders' holds protected. Credit exposure must include outstanding invoices and confirmed uninvoiced commitments without double counting. No generic adjustment may be relabeled as a sale to bypass these requirements. Production deployment, backup restore rehearsal, monitoring and operational access review remain outstanding.

Browser QA used a disposable customer, product and warehouse only in the test database. A 5-piece receipt followed by a 3-piece hold displayed on-hand 5 / reserved 3 / available 2. A decrease of 3 failed with the held-stock warning; a decrease of the 2 available pieces succeeded and showed fully reserved 3 / 3 / 0. Release restored available 3 and enabled draft cancellation while retaining hold history. Hold/release reviews and tables fit a 390px viewport, and inventory fit 1024px with contained table scrolling. All QA holds, stock postings, customer/catalog records and the temporary staff account were removed afterwards.
