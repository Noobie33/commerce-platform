# Staff profile photos and persistent local demo

## Staff profile photos (schema 26)

My profile now supports selecting, previewing, saving, replacing and removing your own photo. The same avatar appears in the sidebar and header, with the name initial as fallback. Only an authenticated staff member can read/change their own photo; there is no arbitrary staff ID endpoint or public storefront image route. Existing origin, CSRF, forced-password and session protections apply. The database function checks current active user/session state again before writing.

JPEG, PNG and WebP inputs are limited to 5 MiB and 16 million decoded pixels. Signature/decoder validation and animation rejection reuse the existing image pipeline. Reception and processing are bounded; two in-flight profile uploads are allowed per API process. A stripped 256x256 WebP centre crop is saved, with a 256 KiB database constraint. The page explains the square avatar and original-discard behavior before saving. This is a profile avatar policy; product originals and product-image limits are unchanged. No external image service or new dependency is needed.

One small current avatar per staff account is kept in private database storage, so updates/removal and audit commit atomically and existing database backups include avatars. This bounded account image is deliberately separate from the large product-media store. Originals, EXIF/location metadata, filenames and obsolete photo bytes are not retained. Only revision metadata is audited. Removal leaves a revision tombstone so a delayed upload cannot resurrect an old image. Stale writes return conflict; the interface reloads the latest revision for review. Runtime roles can execute only scoped photo functions, not directly read/write the storage table. Down migration refuses to discard photo revisions. No production deployment or distributed image-processing guarantee is claimed.

## Persistent demonstration environment

The owner requested sample data remain available for hands-on exploration. The dedicated commerce_platform_demo database, restricted migrator/app/video-worker logins and separate media directories keep all examples apart from commerce_platform_dev and automated commerce_platform_test. The normal business dataset is not seeded. Demo sign-in uses a distinct cookie name so it does not replace a normal staff session on the same loopback hostname. Demo mode refuses production and another database name. Keep demo credentials and data local.

Run npm run start:demo after a full build. Staff UI: http://127.0.0.1:4100/admin . Customer preview: http://127.0.0.1:3100 . Local generated sign-in details are in .local-setup/demo-login.txt; no password is committed or printed. The header says Demo workspace and the storefront says Demo brand. Stopping/restarting services retains sample data. After restarting Windows, run the same demo command; the process must stay running while exploring.

One-time preparation uses node --env-file=.env.setup src/scripts/provision-demo.mjs, migrations plus restricted grants on the new database, and node --env-file=.env.demo src/scripts/seed-demo.mjs. Provisioning refuses name collisions and does not reset existing credentials. Seeding refuses an existing staff/product dataset; it never resets user experimentation or automatically deletes partial state. Preserve local configuration if interrupted and inspect before retrying. Development/test-only migration and cleanup safeguards remain unchanged.

Included: eight published generated product examples plus a hidden draft, a mixed photo/video product, an approved size guide, warehouse/store locations, opening stock and a warehouse-to-store transfer, three fictional suppliers/customers, and sample purchase and retail sales drafts. Example stock postings and drafts go through normal authenticated audited business APIs. No real contacts, payments, supplier obligations or real merchandise are asserted. Website ordering remains closed; a wishlist is not a cart or stock hold.

Suggested walkthrough: browse Catalog and product content/media; compare website cards, filters, quick view, photo enlargement, size guide, video and wishlist; open Inventory to see warehouse and store balances/history; open Purchasing to edit/issue the sample draft and follow receiving/invoice/payment screens; open Customers and Sales to explore a retail draft; open My profile to change the demo avatar. Finance pages may remain empty until the corresponding workflow is performed. Demo edits affect only demo data. Do not enter real personal or business data there.

## Acceptance

The existing business database upgrade requires a restore-verified consistent schema-25 backup and unchanged prior-table fingerprints. Browser upload/remove and persistent demo navigation are separately checked before handoff. Full exact-commit CI remains the final regression gate.

The demo catalog shows eight published examples, while staff see nine products/ten SKUs. Warehouse on-hand is 315 pieces after the 20-piece transfer.
