# Private product video intake and background processing

Schema 23. This adds a local-development staff workflow over the [validated preparation engine](PRODUCT-VIDEO-PIPELINE.md). Upload, processing, private review and website publication are separate states. Public video and the customer Next.js gallery are not enabled by this migration.

## Staff workflow

Catalog > select product > Product videos. A catalog reader can inspect private status, ready playback/poster and history. A global catalog manager can upload MP4/MOV, download retained originals, edit a descriptive label, assign an active variant or the whole product, set video order, cancel/retry processing and remove an item from the product. Actions require a reason and current video revision. A separate catalog.media.review grant permits reasoned private approval/revocation; approval requires a prepared file, saved description, explicit rights/suitability confirmation and verified playback/poster bytes. Unsaved metadata must be saved before approval. Metadata changes clear prior private approval.

Upload percentage is actual browser transfer progress. 100% transfer is followed by confirmation that the private queue entry committed. Background work continues after the dialog closes. Worker commit hints update a clean visible list through the existing authenticated live channel; dirty forms pause background reconciliation. A manual status check remains a recovery control. A stale action must reload current facts rather than overwrite another action.

States: queued -> processing -> ready, with failed/cancelled/removed states and retained history. Ready means sanitized private playback/poster exist; it is not an approved public product. A malformed/unsupported clip fails privately and keeps its original. Transient processing/tool failures retry after a delay, up to three attempts. A user retry also respects that attempt budget. Remove is a retained soft removal, not deletion of originals/history; removed items can be inspected through Show removed videos, while their media routes close. A retention/purge policy is future work; no purge endpoint was added.

Initial operational ceilings are eight non-removed videos per product and 24 queued/processing jobs across the database, stored in migration-owned catalog_video_policy. They prevent accidental disk/processing exhaustion and are not permanent brand requirements. Source size/duration and format limits remain in the video policy. Changes to ceilings require reviewed local operational/migration work; an owner-editable settings screen is not introduced here.

## Request and file safety

All uploads pass the existing session, global permission, Origin, JSON/X-Requested-With equivalent and CSRF checks before consuming file bytes. Only raw MP4/MOV MIME bodies are allowed on the explicit upload route. The web server streams to a private exclusive quarantine directory with length/size/deadline checks and a SHA-256 hash; it never invokes a decoder. Complete bytes are synced before the job is committed. A transaction commits the queued row, retained event, audit and minimal idempotency response together. A lost response retries with the same key; concurrent identical requests produce one job. A different body/actor cannot reuse the key. A definitely unreferenced failed upload is cleaned; an uncertain commit preserves the file for reconciliation rather than deleting a potentially referenced source.

The worker verifies source size/hash, then reuses V1 inspection/conversion without changing originals. Quarantine sources and prepared bundles stay outside web asset trees. Only authenticated staff routes serve hash-verified bytes. Original download requires management permission and uses an attachment/sandbox response. Private playback supports a validated single byte range and no-store; unapproved ready media is visible only to authorized staff reviewers. Removed/missing/tampered media is denied. At most two active media responses are admitted; video responses do not expose file paths, integrity hashes, lease tokens or worker credentials.

## Durable jobs and restricted worker

New tables: catalog_video_policy, catalog_product_videos, catalog_video_events and catalog_video_requests. No prior content/profile/SKU/stock/finance or public-release data is mapped, rewritten or automatically published. Runtime has read access and narrow staff-action function execution, not raw job/history writes or worker mutation functions. SQL independently checks current actor permissions before replay.

Worker accounts commerce_dev_video_worker and commerce_test_video_worker use distinct generated credentials in ignored .env.video-worker files. They cannot read staff/customer/financial tables or write queue rows directly. They receive only schema-version access and narrow claim/heartbeat/finish/storage-reference functions. Startup rejects elevated or overly broad worker privileges. Native FFmpeg/FFprobe children receive an OS-variable allowlist rather than database/password/token environment variables.

A separate process claims a job using a database-wide admission lock and a random fenced lease. A heartbeat extends a live 60-second lease. Expired leases recover to a delayed retry, respecting the attempt budget; concurrent workers do not process two active jobs. Completion requires the current unexpired token. Cancellation/removal clears it, so late workers cannot resurrect cancelled jobs. Ready metadata and an immutable event/audit commit together. Events explicitly distinguish worker actions from staff actions while retaining the original initiating uploader identity. Shutdown interruption queues valid media for retry rather than mislabelling it as invalid.

Prepared output files and their manifest are synced before ready state is committed. If completion is uncertain, cleanup checks database artifact references before removing only its own unreferenced attempt. video:reconcile-local reports missing and unreferenced storage without deleting retained files. File integrity is rechecked during preparation, private delivery and review. Windows filesystem durability/ACLs and power-loss recovery still need production deployment acceptance.

## Local startup and deployment boundary

start:local starts the API plus a separate video worker when explicit local intake and its worker configuration exist. The worker process receives only OS variables plus its own worker file, not the API/migration connection environment. API shutdown stops the worker; worker failure leaves durable jobs queued rather than crashing the business API. Standalone video:worker-local and report-only video:reconcile-local commands remain available. video:verify-local checks aggregate job/history invariants without exposing identities or content.

Intake requires VIDEO_INTAKE_MODE=local-development and a loopback HOST. NODE_ENV=production always rejects intake and worker startup. This release is for the trusted local development workflow, not internet-facing ingestion. Separate database credentials and sanitized process environments are not an OS security sandbox. A dedicated low-privilege OS worker/container, restricted filesystem permissions/network, malware/decoder maintenance, OS CPU/memory quotas, upload abuse controls, disk/backup/retention capacity, crash recovery drills and realistic loads remain gates before deployment. No paid service or new Node package is required.

## HTTP contract

GET /api/v1/catalog/products/:id/videos?page=1&removed=1 optionally includes removed items. POST the same product route receives raw bytes with X-Product-Version and X-Idempotency-Key. GET /api/v1/catalog/videos/:id/history has paginated immutable events. POST /api/v1/catalog/videos/:id accepts metadata/retry/cancel/remove; POST /review accepts approve/revoke under its separate permission. GET /original, /playback and /poster remain staff-only; no /api/v1/store video route was added.

All staff actions use current video revisions and idempotency keys; clients cannot assign state, source hashes, lease tokens, attempt counts or artifacts. Existing product revisions are checked at intake but not incremented by private media work. Product description/content review and photo-only publication remain independent until the explicit mixed-media public-release migration.

## Verification and remaining gates

Focused acceptance uses generated clips and disposable accounts/products in commerce_platform_test. It covers unauthenticated/reader/CSRF rejection before file intake, real concurrent duplicate streams, original identity, scoped SQL privileges, actual background conversion, range/original privacy, independent review, variant ownership, tampered files, failed media, expired/stale leases, cancellation/retry, audit rollback, permission revocation before replay, reference-aware retention and additive migration down/refusal/reapply. Unit tests cover strict actions/ranges and production-disable rules; the complete prior unit/database/codec suite remains required. Desktop/mobile browser QA and restore-verified development cutover are completed before handoff.

Remaining V3: ordered mixed photo/video public snapshots, captions/transcript/audio policy, accessibility/rights completeness, public review/revocation binding, public byte-range delivery/caching and the actual Next.js gallery. Private approval alone cannot satisfy or bypass those gates. No customer checkout, finance, POS or manufacturing behavior is changed.
