# Customer account sign-in foundation (schema 27)

## Delivered scope and deliberate gate

The Next.js storefront now has a working My account entry, a responsive sign-in form, an own-profile view and current-session sign-out. Customer identity, password hashes, sessions, throttles and events are separate from staff identity and from ERP customer/contact records. An email match does not automatically link existing ERP history. This advances SF-14; it does not mark registration, recovery, address book, account wishlist, orders or checkout complete.

Sign-in is closed by default. CUSTOMER_ACCOUNT_MODE=preview is accepted only for the named local development/test/demo databases outside production. Real customer enrollment remains closed until verified email delivery, recovery, abuse controls and rollout acceptance are implemented. There is no fake email verification or working-registration claim, and no public provisioning or account directory endpoint. The main preview remains closed; the retained local demo has one explicitly prepared fictional account.

## Authentication and browser boundary

The implementation reuses the existing fixed-cost scrypt password service, including unknown-user dummy work and bounded hashing concurrency. Invalid, inactive and unknown accounts return the same credential error. Persistent per-email and source buckets bound attempts within fifteen-minute windows. The API sees the local storefront server as its source; trusted production client-address handling and load/abuse controls remain deployment gates. No untrusted forwarding header is accepted as identity.

The API generates a fresh random 256-bit opaque token and stores its SHA-256 hash. Login rechecks the active account/password under a transaction and commits the session with an audit event. Reads recheck activity, revocation, eight-hour absolute expiry and thirty-minute idle expiry. Recent activity is renewed at most once per minute. Logout uses a separate random customer CSRF value, locks/revokes the current session, and writes exactly one event for repeated/concurrent requests. No password, token, CSRF value, email or IP is stored in event payloads. Runtime roles cannot create accounts/change passwords or rewrite event history.

The Next.js account routes keep tokens in host-only HttpOnly, SameSite=Strict cookies with Path=/ and eight-hour lifetime. Local storefront ports use distinct cookie names, preserving normal/demo staff and customer logins. HTTPS cookie names use the __Host- prefix and Secure; public TLS deployment is not enabled by this increment. Tokens never enter localStorage, public JSON, React props or HTML. Customer CSRF stays in the server-to-server path.

Browser writes require the exact configured storefront Origin, a custom request header and JSON; bodies are streamed with 8 KiB/five-second bounds. The API controller uses a separate customer-only request guard requiring a loopback same-origin server request for writes. Staff endpoints retain their original guard/CSRF rules. Only the selected customer token is forwarded; arbitrary browser Cookie, Authorization, forwarding headers and query parameters are not. API responses are bounded, parsed and allowlisted before browser display. Account responses are no-store. The page rechecks on foreground/network recovery and notifies same-origin tabs through a credential-free BroadcastChannel message. Temporary failures offer retry rather than fabricating a signed-out session.

Guidance consulted: [OWASP Authentication Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html) for generic errors/throttling and [OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) for opaque tokens and cookie handling. This is a bounded local preview, not an assertion of complete compliance or launch readiness.

## Demo operation and retained data

The existing demo staff account, nine product fixtures, photos/video, guides, stock, suppliers, customers and drafts are retained. The additive seed-demo-customer.mjs command checks the demo database explicitly and does not reset credentials or existing records. Customer sign-in details are in the ignored .local-setup/demo-customer-login.txt file; staff details remain in demo-login.txt. Open http://127.0.0.1:3100/account for the customer and http://127.0.0.1:4100/admin for staff. npm run start:demo starts the same retained environment. No paid dependency or messaging provider is introduced.

The wishlist remains explicitly browser-local after sign-in. Account-backed saving/guest merging will be a separate increment so that account switching cannot silently attach another person's saved IDs. Account editing, verified registration/recovery, session management across devices, expiry cleanup, confirmed orders and production monitoring/load/security controls remain acceptance work.

## Acceptance gates

Unit cases cover credential shape/normalization, preview-only configuration and DTO/cookie isolation. Real PostgreSQL/HTTP/production Next.js checks cover staff/customer separation, generic errors, current user, token hashing, idle/absolute expiry, revocation/deactivation, wrong-CSRF and foreign-origin denial, idempotent logout, audit rollback, throttling, private-field stripping, cookie attributes, request bounds, protected staff behavior and migration up/down refusal to discard account history. Existing business migrations are unchanged. Development cutover requires a consistent restore-verified backup and unchanged prior-table fingerprints; demo migration preserves sample records. The 94 database-free cases and 12 focused customer PostgreSQL/Next.js cases pass locally. Full exact-commit CI and desktop/mobile browser checks remain the final gates before reporting this slice complete.

Observed browser acceptance: incorrect credentials showed a generic error, successful sign-in displayed only the prepared customer name/email, reload retained the session, and sign-out updated a second tab without refresh. Mobile sign-in, account/wishlist/menu controls and menu navigation were exercised at 390px with no horizontal overflow. The demo customer is left signed in for the owner walkthrough. Both main and demo schema upgrades preserved fingerprints of all 80 prior data tables. Main customer sign-in remains closed; the demo alone enables the prepared account.
